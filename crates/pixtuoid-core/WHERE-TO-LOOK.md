# pixtuoid-core — where to look

Answers for the questions indexed in [`CLAUDE.md`](CLAUDE.md)'s
"Where to look". Each entry is self-contained — grep for your question
and read that one, or read the file end to end when mapping the crate.



- "How does the per-agent state machine work?" → **two stacked layers, both extracted into named modules so the reducer reads as a coordinator.** **Layer A** = `state/fsm.rs`: the single-slot transitions (`enter_active`/`enter_delegating`/`enter_waiting`/`arm_pending_idle`/`settle_to_idle`/`mark_exiting`/`rename`), each independently unit-tested; `accumulate_active_ms` lives here once (was copy-pasted 4×). **Layer B** = `state/scope.rs`: the parent↔subagent tree ops. **Invariant:** `fsm.rs` mutates ONE slot; the **cross-slot correlation** (`active_tasks` suppression, `gated_before_waiting` permission, the hook-wins dedup) stays in the REDUCER's layer — it spans slots and is NOT the FSM. The seven correlation maps' bookkeeping (entry types, TTL consts, freshness predicates, the one `gc(now)`) lives in `state/correlation.rs` as a `Correlation` struct owned by the reducer (`self.corr.*` — intra-layer extraction, not a new layer); the DECISIONS (which arm fires, what gets suppressed) stay in `state/reducer/mod.rs`. The reducer decides *whether/which* transition fires; `fsm` decides *how* the slot changes. Don't move the correlation maps onto `AgentSlot`. **Suppress-restore is gate-aware**: a suppressed child hook event restores a Waiting parent to Delegating ONLY when `gated_before_waiting` is absent or holds a Task tuid (∈ `active_tasks`); an ordinary tuid means the parent's OWN parallel-tool permission prompt is still pending — keep Waiting, keep the gate (pinned by `suppressed_child_event_keeps_parents_own_parallel_tool_gate`).
- "Why is the subagent's sprite the right one and not the parent?" → `reducer::Reducer::apply` does subagent-leak suppression via `active_tasks` before applying. `claude_code::decode_cc_line` emits `AgentEvent::Rename` from `attributionAgent`.
- "How does multi-source decoding work?" → `JsonlWatcher` takes `LineDecoder` and `LabelDeriver` fn pointers (Strategy pattern via fn pointers, not traits). The registry is 13 rows (12 `Agent` + 1 `Daemon`): hook-only sources carry `transcript: None` (the `Transcript{line_decoder, id_from_path, cwd_extractor}` bundle) and the daemon a typed `SourceKind::Daemon` row — absent capability is TYPED, not stubbed. Uniform-signature unused params persist ONLY in the JsonlWatcher wiring of the 6 transcript-bearing sources (always-false `SessionEndChecker`s with WHY comments) — deliberate fn-ptr Strategy uniformity; don't trait-ify it. The `LabelDeriver` now DEFAULTS to the source-prefixed `derive_prefixed_label` inside `JsonlWatcher::new` (the `with_cwd_deriver` idiom); only **CC** overrides it via `with_label_deriver` (its empty-cwd project-dir fallback), so the other five sources dropped their byte-identical wrapper fns. **The `IdDeriver` defaults from the source's REGISTRY ROW** (`registry::id_deriver_for`, applied in `JsonlWatcher::new`) — no source calls `with_id_deriver` any more; the builder survives only for a watcher over an unregistered source (a test naming its own). That row is read a SECOND time by `harness::Drive`'s first-sight seed, which is why the derivation left the "deliberately not in the table" list (see `registry.rs`'s header): an offline driver keying it any other way registers nothing and misreports it as a decoder failure. CC wires `claude_code::decode_cc_line` + `.with_label_deriver(cc_derive_label)` (the SOLE label-deriver override; plus the optional `with_liveness_probe` seam → `live_cc_session_ids` — see the first-sight-gate sharp edge); Codex wires `codex::decode_codex_line` (default label deriver; plus the same probe seam → `live_codex_rollout_ids`, open-FD binding via `fd_probe`); Antigravity wires `antigravity::decode_ag_line` (default label deriver). **Copilot CLI (`copilot`) is TRANSCRIPT-ONLY** (`copilot::decode_copilot_line`, default label deriver, NO hook target/decoder — richer than Codex: the whole lifecycle incl. permission + sub-agents is persisted to `<copilot_home>/session-state/<id>/events.jsonl`). Two real-byte sharp edges: (a) the **session id is the PARENT-DIR UUID** of `events.jsonl` (the filename stem is the constant `events`) → `copilot_id_from_path` derives the containing dir, overridden via `with_id_deriver`; (b) **sub-agents INTERLEAVE in the root file** (no per-agent split), keyed on the top-level envelope `agentId` (== the spawning `task` tool's `data.toolCallId`) — `subagent.started`→child `SessionStart`(+`Rename` from `agentDisplayName`), `subagent.completed/failed`→child `SessionEnd{as_child}`, and a line carrying `agentId` attributes to that child; `subagent.completed` is minimal on disk (no model/token fields — don't require them). `task` toolName→`ToolDetail::Task`; `permission.requested`→Waiting / `permission.completed`→clear; `session.shutdown`→root end; the `ephemeral`-flagged streaming types (incl. `session.idle`) never hit disk and are ignored. Defensive parse (skip-bad-line, never panic) for upstream embedded-newline / U+2028 corruption (copilot-cli #2649/#2012). **Oh My Pi (`omp`, omp.sh) is ALSO TRANSCRIPT-ONLY** (`omp::decode_omp_line`, default label deriver, plus the liveness-probe seam → `live_omp_session_ids`, open-write-fd binding via `fd_probe` like Codex (#518) — omp keeps a for-lifetime append fd on each session file; it runs under Bun so BOTH kernel comms `bun` and `omp` are probed, and the under-root `.jsonl` join carries the precision (fd MODE unchecked — a bun tool READING an old transcript is the accepted intermittent-resurrection residual); `omp_probe_root` attaches it only for the first-party `.omp/agent/sessions` / resolved-`omp_agent_dir()` layout. NO hook target — omp has no shell-hook seam, only in-process TS extensions): the whole lifecycle persists to `<omp_agent_dir>/sessions/<encoded-cwd>/<ts>_<uuidv7>.jsonl` (`omp_agent_dir()` honors `PI_CODING_AGENT_DIR`, else `~/.omp/agent`; the opt-in XDG split + `OMP_PROFILE` are deliberately unmirrored). Wire facts (repo-derived @ v16.3.12, ff1fe5f; byte-real anchored @ 16.4.0, 2026-07-10 — the omp conformance fixtures are sanitized live captures and `verified_version` is "16.4.0"): line 1 is a fixed-width 256-byte `type:"title"` slot REWRITTEN IN PLACE on rename (never re-read by a tail cursor), line 2 the `type:"session"` header (top-level `cwd` → the shared extractor); assistant `message` entries carry `type:"toolCall"` content blocks (`{id,name,arguments}`) → ActivityStart, `role:"toolResult"` → ActivityEnd (the duplicate `custom`/`tool_execution_start` entry is deliberately NOT decoded — same tool_use_id would double-count); the built-in `ask` tool (the user-question gate, #519) additionally emits `Waiting` right after its ActivityStart — the Start binds the reducer’s `gated_before_waiting` to the ask’s own tool_use_id, so the answer’s toolResult (ActivityEnd, same id) resolves the Wait; a `custom`/`session_exit` entry is appended+flushed on every clean teardown incl. SIGINT/SIGTERM (→ SessionEnd + the session-ended checker; SIGKILL writes nothing → stale-sweep). **Subagents are SEPARATE NESTED FILES** (`<parent-path-minus-.jsonl>/<taskId>.jsonl`, recursive; linkage is the PATH — the child header has no parentSession): `omp_id_from_path` keys the whole stem chain (`<root-stem>/Alpha/…`, so a task id never collides across sessions) and the header decode emits a parented SessionStart that enriches the watcher's parentless first-sight registration. Keying: `sessionId` == the transcript's parent-DIR name → `grok_id_from_path`; content carries NO cwd anywhere, so the watcher's `with_cwd_deriver` PATH fallback (`grok_cwd_from_path`: percent-decode the group dir, `.cwd` file for the >255-byte slug+blake3 form) fills first-sight cwd — without it every grok slot would ride the unknown-cwd 3-min reap. Hook mapping: `session_start`→SessionStart (its public `source` field is the start REASON "new"/"load" — the CC ghost trap, never read for attribution); `user_prompt_submit`→SessionStart (the resurrect carrier — see caps); `pre_tool_use`→Identity+Start; `post_tool_use`/`_failure`/`permission_denied`→Identity+End (denial resolves the Waiting gate — approval fires NO hook, the tool's own post_tool_use does); `notification{permission_prompt,elicitation_dialog}`→Waiting, `{idle_prompt,agent_error,task_complete}`→deliberate quiet drops (task_complete announces a BACKGROUNDED shell/monitor task finishing — no `toolUseId`, and its spawning tool call already Ended at backgrounding time, so there is nothing to close). **The `notificationType` VALUE vocabulary is deliberately defense-#2-ONLY**: upstream types the field as a bare `String` (`xai-grok-hooks/src/event.rs`) and mints the values at scattered dispatch sites, so NO declaration owns them — an anchor could only be the weak identity grade and a name-presence sweep over call sites is the #793 false-positive machine. The `other` arm's composed `notification:{type}` breadcrumb IS the detector (the antigravity class); don't re-propose a drift-watch row. A new value joins the quiet arm by READING its upstream dispatch site and judging it lifecycle-free, never from a log sighting; `subagent_stop` AND `subagent_end`→child SessionEnd{as_child} (upstream's finish site fires the SubagentEnd ALIAS while the docs name SubagentStop — both registered, both decoded, drift-watched). **The b1 trap:** grok's `spawn_subagent` defaults `background=true`, where `post_tool_use` fires at SPAWN — so `grok_tool_detail` mints `ToolDetail::Task` ONLY for an explicit `background:false` (blocking; End==completion), or the b1 drain-cascade would evict the LIVE child ~2.5s after spawn. Background children lose only the parent's Delegating pose: they're first-class (child-keyed tool hooks — no `active_tasks` suppression needed; wire-carried ends). **Cross-fire guard:** grok scans `~/.claude/settings.json` AND `~/.cursor/hooks.json` hooks BY DEFAULT and fires those shim commands with GROK envelopes → they arrive tagged `claude-code`/`cursor` as duplicates of the grok-tagged copy; `decode_hook_payload` drops any `hookEventName`-carrying payload whose tag isn't grok, QUIETLY (trace, pre-custom-decoder — else CC/cursor Err per tool call). **Exit/liveness:** `session_end` does NOT fire on a plain TUI quit (the event loop breaks without draining the session actor) → caps `{has_exit_signal:false, resurrects_on_prompt:true}` (grok joins Codex on the short-idle reap; every prompt's `user_prompt_submit` re-registers a swept-live session — and the vouch exemption covers ROOT sessions only: grok subagents are in-process and never in `active_sessions.json`, so an idle-but-alive grok CHILD reaps Codex-child-style, self-healing via its wire-carried end/activity). LEADER MODE (#638) — **grok leader-mode sessions are DELIBERATELY UNVOUCHED (#826); the vouch was deleted, not repaired.** `--leader` runs the agent (file writes + hooks) in a shared LEADER process while `active_sessions.json` records only each TUI CLIENT's pid, so a client detach — the feature's NORMAL operation — reads as the session's exit. #638 added a secondary vouch off `leader.sock` to close that; it never fired on any platform, because the now-deleted `leader_socket_owner` asked `fd_probe::open_vnode_paths`, which reports VNODE descriptors only and a unix socket is not one (macOS `PROX_FDTYPE_SOCKET`; Linux `/proc/<pid>/fd/N` → the non-path `socket:[inode]`) — still pinned by `fd_probe`'s `open_vnode_paths_never_reports_a_unix_socket`. **Repairing the probe was adjudicated against, twice over.** (1) The probe was the SECOND defect: the deleted `augment_with_fresh_sessions` bound the leader with `or_insert`, so the registry's CLIENT pid still won — and that is the pid `ProbeLadder::fold` hands the `ExitWatch`, so the client's death ended the session in MILLISECONDS while the leader binding could only migrate in on the 60s poll. A byte-perfect probe could not reach the symptom. (2) The vouch was mtime-derived, so it EXPIRED while the session lived, and an id leaving a HEALTHY snapshot is exactly the negative-vouch trigger (~240s) where the unvouched session survives to the 300s short-idle reap; the lever was arithmetically zero (150 + 150 = 300), and a firing vouch re-admitted the parked transcript at cursor 0 (full replay + phantom `SessionStart`). **Why no correct fix exists in-tree**: session→leader ownership lives ONLY in `leader/server.rs`'s in-memory `session_driver`/`session_subscribers` maps. Every disk-observable surface answers a DIFFERENT question — `active_sessions.json` gives the client pid, `leader{suffix}.lock` gives the leader's pid + liveness (flock, pid in the file) but not which sessions, and the transcripts carry no ownership signal because the writer opens and drops the fd per append (`session/storage/jsonl/mod.rs::append_jsonl_line_sync_with` — verified, so no Codex-style open-fd probe is possible). The control protocol has 9 `ControlCommand` variants and NONE lists sessions (`WorkspaceStatus.sessions` is the computer-hub workspace's, a different concept). So any in-tree fix is a proxy with its own failure mode, which is what #638 was. **The real fix is upstream exposing the fact** — a `ListSessions` control command, or a `leader_pid` field on the registry entry; either one collapses the whole class. Tracked in #839. Leader sessions meanwhile ride the pre-#638 path (mtime gate + short-idle reap + prompt resurrect), which is what they have done for the feature's entire shipped life. - "Why don't old idle sessions show on startup?" → `source::jsonl::walk::should_seed_at_eof` (the first-sight gate inside `walk_jsonl`). Checks `check_session_ended` (tail-scans last `TAIL_BYTES` for `session_end`/`SessionEnd` markers) and seeds the cursor at EOF for any file whose last AGENT ACTIVITY is older than `DEFAULT_INITIAL_WINDOW` (1 hour) — no `SessionStart`. "Last activity" is the source's `ActivityRecency` over that same tail where it supplies one (CC only), else the file mtime; see the sharp edge for why CC's mtime lies. An mtime outside the 1-hour window **OR** a `session_end` marker is the freshness gate, and it runs on every first-sight path (seed / 250ms rescan / 60s poll / notify), not only startup. Exception: a session the **liveness probe** vouches for (CC's `sessions/<pid>.json` registry; Codex's open-rollout FD binding; omp's open-write-fd binding — see the sharp edge above) is never gated on MTIME, however old; the `session_end`-marker half still gates it (a vouch is a liveness proxy, a terminator is the source's own report).
