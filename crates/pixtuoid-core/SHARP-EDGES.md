# pixtuoid-core — known sharp edges

Indexed one line each in [`CLAUDE.md`](CLAUDE.md). These look like bugs and are deliberate design — read the entry before "fixing" one.

- **There is NO core `render` module and no core render trait.** `blit_frame` (the scene painter's primitive) is the only pre-scene-split render helper that stays; `TuiRenderer` keeps an inherent `render`, and the e2e fixture captures scenes as a plain `Vec<SceneState>` in `tests/e2e.rs`. New render targets go through `pixtuoid_scene::floor::render_floor` / `pixel_painter::render_to_rgb_buffer` (workspace invariant #1) — do NOT reintroduce a core render trait or module.

- **`walkable.rs` is coherence-bound to this crate — it did NOT move with the sim-geometry cluster.** When layout/pose/physics moved to `pixtuoid-scene` (the engine owns its geometry), `WalkableMask` had to stay: it is a type ALIAS for `Grid<bool>` whose obstacle ops (`new_open`/`mark_blocked`/`mark_walkable`/`is_walkable`) are an inherent `impl Grid<bool>`, and Rust's orphan rule pins an inherent impl to the crate that owns the type — `Grid` is core vocabulary (`Frame`/`RgbBuffer` newtype it). Reversing the #333 alias back to a wrapper struct, or an extension trait, were both already adjudicated against (see the comment on the impl). So core keeps the mask VOCABULARY; the producers (`pixtuoid_scene::layout::mask`) and consumers (pathfind/pose/motion) live crate-up.

- **A daemon's runtime identity is the SOURCE's own wire fact, and for OpenClaw that is the resolved gateway PORT — not the profile, not the pid.** `SceneState::daemons` is keyed `(source, DaemonInstanceId)` because OpenClaw officially supports several isolated gateways on one host, each on its own base port. Three candidate keys were adjudicated and rejected: the **profile** (`OPENCLAW_PROFILE`) is an INSTALL scope that never reaches the hook wire, one profile may restart on a different port, and — the decisive one, verified live — profile↔gateway is **1:N**: `gateway run --port` lets ONE profile host several concurrent gateways, which then share its name AND its config, so the profile cannot tell them apart at all while the port can (see the binary guide's `connect openclaw` sharp edge); the **pid** changes every restart, so the mascot would churn (walk out + walk in) on each one; the **session id** is many-per-gateway. The port is distinct per live gateway — upstream REQUIRES each one to run on its own base port, which is what makes a multi-gateway host multi-gateway at all (not a kernel guarantee: `SO_REUSEPORT` and per-interface binds mean the kernel would tolerate a collision; two gateways deliberately configured onto one port would merge into a single mascot, the pre-change behaviour, and nothing worse) — and STABLE across a restart of the same one, which is exactly the pair the renderer needs. The two identity concepts stay separate on purpose: `DaemonInstanceId` is stable, `DaemonPresence::current_pid` is the process INCARNATION that `GatewayUp` rebinds — that split is what makes a late exit receipt for a replaced process a no-op. **No `PidIdentity{pid,started}` generation guard is needed on this path** (unlike the focus channel's): the receipt is synthesized at death and rides the SAME single-consumer presence channel as the hook deltas, so it is applied BEFORE the replacement's `GatewayUp` could rebind — the plain `current_pid == Some(pid)` equality already covers it, and a pid recycling into the same slot within that window needs a full pid-space wrap. Adding the marker here would be cost with no reachable failure to prevent. (`FocusChannel` is also structurally agent-only — a mascot isn't clickable — so the daemon path was never "the one consumer missing the guard".)

- **`GatewayDown` CREATES an absent instance; `PidExited` never does — the asymmetry is the point, not a hole in the creation-polarity rule.** Both look like "death" deltas, so a review will ask why only one is non-creating. The difference is PROVENANCE: `gateway_stop` is a first-hand WIRE report from a process that was demonstrably alive when it spoke (the plugin runs IN the gateway), so materializing it and playing the walk-out is honest — the mascot leaves the way it would have if we'd attached a second earlier. `PidExited` is SYNTHESIZED locally by our own exit-watch drain, possibly long after the fact and possibly for a process the gateway has already REPLACED, so creating on it resurrects a phantom mascot for a gateway that is dead (the fbe26049 class) — hence the `current_pid == Some(pid)` guard and the non-creating arm. Secondary: making `GatewayDown` non-creating would be inert on the real wire anyway, because the plugin stamps `_pid` on every event and the decoder PREPENDS a `PidSeen` to the same batch — genuine proof of life, which creates the entry before the `GatewayDown` applies. Don't "harmonize" the two arms.

- **A `gatewayPort`-LESS OpenClaw envelope falls back to ONE documented legacy instance instead of being rejected — deliberately.** Installing the plugin is a one-shot `connect`; upgrading the pixtuoid binary does NOT re-render the on-disk `index.js`. So a user upgrading into the instance-keyed world still has the OLD plugin stamping no port, and a hard reject would make their lobster silently VANISH — a regression shipped to every existing user, in exchange for purity. The fallback instead reproduces the pre-change behaviour EXACTLY (two stale-plugin gateways still merge, which is what they did before — never worse) and fires `drift::missing_field`, so `pixtuoid doctor` + the footer drift nudge tell them to reconnect. A port that is PRESENT but unusable (0, negative, out of `u16`, non-integer) is a different case — a bug or a hostile sender, never a compatibility question — and REJECTS the envelope. Don't "tighten" the absent-field arm into a reject without also solving stale-plugin refresh.

- **The two pid→fan-out shells (`HookPidWatch` in `hook/pid_watch.rs`, the daemon's `PresenceExitWatch` in `daemon/native.rs`) stay SEPARATE — do NOT hoist a generic `PidFanout<K>`.** The DEEP primitive is ALREADY shared at the right seam: `source/exit_watch.rs::ExitWatch` (kqueue/pidfd/poll, the ESRCH/EPERM/ENOSYS registration race + closed-handle rejection, ~560 lines) takes a pid and emits a raw pid on an `UnboundedSender<i32>`; both shells feed it one. So all the real complexity sits BELOW the seam, and only a ~12-line bookkeeping shell (the `pid → HashSet<K>` map + register + take-on-death) sits above it — and that shell's two instances DIFFER at every load-bearing point: the emitted event (`AgentEvent::SessionEnd` vs `PresenceMsg::PidExited`), the CHANNEL (the one bounded-async AgentEvent channel vs the unbounded-sync presence SIDE channel — invariant #2's deliberate two-channel split), and the handle shape (`Arc<ExitWatch>` cloned per hook connection vs a single owned multiplexer). A `PidFanout<K>` would take K + register + an emit-closure + the channel + the handle-wrap as parameters — an interface nearly as wide as the ~15-line body it hides (a textbook SHALLOW module) whose one seam would straddle invariant #2 exactly where the two designs must diverge. `daemon/native.rs` already records the call in-code ("reuse the AGNOSTIC `ExitWatch` … NOT `HookPidWatch`, which emits an AgentSlot-shaped `SessionEnd` the non-slot mascot can't consume"). Adjudicated against in the architecture-deepening sweep — the shared surface is too shallow to earn a second seam.

- **The `native` (default) feature gates the ASYNC SOURCE RUNTIME, not the decoders — and the gates are MODULE-level, not item scatter.** `default-features = false` drops tokio/notify and everything behind `#[cfg(feature = "native")]`: `hook/`, `jsonl/`, `manager`, the liveness probes (`cc_probe`/`fd_probe`/`exit_watch`), `source/native.rs` (the `Source`/`DynSource` traits + tagged channel, ONE gate in `source/mod.rs`), and each mixed source module's runtime half — its `impl Source`, watcher wiring, probe attach, `PresenceExitWatch` — which lives in a once-gated `native` sub-module (`source/<cli>/native.rs` for claude_code/codex/antigravity/copilot; `source/daemon/native.rs` for the presence layer), re-exported from the parent so public paths don't move. That leaves the pure decode/reducer/sprite core that compiles to `wasm32-unknown-unknown` (what `pixtuoid-scene` → the `pixtuoid-web` painter build against). **Per-source decoder fns and the registry stay always-compiled on purpose** (registry rows name them as data; `LineDecoder` + `IdDeriver` + `TailActivity` + `SUBAGENTS_DIR` + `is_subagent_path` live in the always-compiled `decoder.rs` for the same reason — `jsonl` re-exports, never redefines). The SECOND, unrelated feature is **`harness`** (NON-default): the offline `Drive` driver, dev-only so it stays out of the shipped lib AND out of the published API surface (`cargo public-api`/`cargo semver-checks` both run on default features). `#[doc(hidden)] pub` — this crate's other answer, used for the registry itself — would keep it off both GATES equally (rustdoc JSON omits hidden items); the feature is chosen because it additionally keeps ~600 lines of scaffolding out of the shipped lib and out of the `--no-default-features` wasm build. A crate cannot turn its own feature on for its dev targets directly, so core's manifest depends on ITSELF by path under `[dev-dependencies]` — the standard workaround (rust-analyzer#20836 does the same), and it covers examples as well as tests, which is what the fuzz/corpus shells need. Don't "clean it up" into a normal dependency: that would ship the harness. When gating new code, follow the pattern: put the whole native half in the module's `native.rs` behind the parent's ONE gate + re-export (a parent file should carry ≤2 item-level `cfg`s — the gate and the re-export), never item-by-item `#[cfg]` scatter. Label-deriver / session-ended fns go NATIVE-side unless an external consumer needs them `pub` in the parent (only **CC** keeps `cc_derive_label` + `cc_session_ended` parent-`pub` for tests + `examples/snapshot/`; since #5 every other source's label deriver rides the `JsonlWatcher` default and its session-ended fn is native-private — consumer-driven, not arbitrary). `just hack` (feature powerset) catches ungated optional-dep use on the HOST target, but wasm32-only breakage (target-gated deps, syscalls outside the gate) surfaces ONLY in CI's `wasm-check` job / a local `just gen-wasm` — host-green ≠ wasm-green.

- **The per-CLI home resolvers MIRROR each CLI's own; the axes deliberately NOT mirrored are listed here** (#880). A resolver shaped `$SOME_ENV else ~/.<cli>` is correct only if someone READ that CLI's resolver and found it generic — where a source tails a transcript, an unmirrored axis is fail-silent: the watcher polls a directory the CLI never writes to, and the office is empty with no error. Audited against the shipped artifact (claude-code 2.1.226, copilot 1.0.78, hermes 2026.8.3, omp `dirs.ts` @ main), the two native resolvers by direct invocation. **Not mirrored, don't "fix" these:** copilot's `--config-dir` flag outranks `COPILOT_HOME` but is per-invocation and unobservable from our process; copilot's XDG dirs are legacy-migration-only (migrated INTO `~/.copilot`, skipped entirely when `COPILOT_HOME` is set); hermes profiles are applied out-of-band by a wrapper exporting `HERMES_HOME`, and `get_hermes_home()` never reads the `active_profile` file — upstream calls the mismatch a bug (`NousResearch/hermes-agent#18594`); CC's `.normalize("NFC")` and grok's `dunce::canonicalize` change the path STRING but name the same directory (macOS lookup is normalization-insensitive; our CC keys are ASCII UUIDs). **Empty vs whitespace:** CC and copilot take `"  "` as a literal relative dir; we treat it as unset, because we cannot resolve a relative override at all (below) and the installer would otherwise create a junk `"  "` dir in OUR cwd. **A RELATIVE override is unmirrorable, not merely unmirrored** — none of them absolutizes one or expands `~`, so each resolves it against ITS OWN cwd; `platform::warn_if_relative_override` passes the value through unchanged and warns. **omp is the deepest**: `PI_CONFIG_DIR` is a directory NAME joined under home Node-style (an absolute value does NOT escape home — Rust's `Path::join` does the opposite, hence `node_join`); `OMP_PROFILE` (winning whenever PRESENT, even empty) else `PI_PROFILE` selects `profiles/<name>/agent`; `PI_CODING_AGENT_DIR` is dropped when it equals the `PI_PROFILE`-derived dir; and XDG (linux+darwin, no override, target must EXIST) **FLATTENS `agent/` away** — which is why `omp_sessions_dir` is its own fn, and why the FD-probe gate compares against it rather than the agent dir. **One omp axis is unmirrorable and is named rather than assumed away**: omp loads `.env` FILES (`packages/utils/src/env.ts` parses `~/.env`, `<configRoot>/.env`, `<agentDir>/.env`, `<cwd>/.env`, fills only keys the process env left unset, then calls `refreshDirsFromEnv()`). So `PI_CODING_AGENT_DIR` or `XDG_DATA_HOME` in a `.env` relocates omp's sessions dir while our PROCESS env shows nothing and we poll the old one — reading those files is the fix if it ever bites. Only hermes and omp have fetchable resolvers, so only they carry `check_upstream_drift.py` rows; CC and copilot live in a closed binary and a napi addon. **That is NOT Antigravity's defense-#2 class** — a decoder sees wire bytes and can breadcrumb, a home resolver aimed at the wrong directory observes NOTHING. Their only defense is re-running the probe matrix when either CLI majors.

- **CC hook payloads DO include `tool_use_id`** in `PreToolUse` and `PostToolUse` (verified by sniffing live payloads). The decoder reads it; the reducer's hook-wins dedup actually fires. **The dedup is asymmetric by event kind (#150)**: a recorded hook End suppresses both JSONL kinds (covers the tool's whole lagged JSONL pair), but a recorded hook Start never suppresses a JSONL End — when the PostToolUse hook drops (best-effort shim), that JSONL End is the only completion signal left, and eating a Task self-End would leak `active_tasks` for the rest of the session. The kind lives in the map *value* (an End overwrites its tool's Start entry) — don't "simplify" to a kind-in-the-key or exact-kind match; both regress a pinned case (`late_batched_jsonl_pair_after_delivered_hook_end_is_fully_dropped`).

- **That hook-wins dedup is ONE-directional — a JSONL-first tool inflates `tool_call_count` by 1 (cosmetic).** The dedup drops a JSONL event only when a matching hook `tool_use_id` was ALREADY recorded; the hook arm is the sole writer of `recent_hook_tool_uses`, and no path drops a hook against an already-applied JSONL twin. So when a tool's JSONL `ActivityStart` wins the delivery race against its hook twin (two independent tokio tasks — the `HookRouter` and the source's `JsonlWatcher` — feed the one `mpsc<(Transport, AgentEvent)>`, and tokio gives no cross-sender ordering), BOTH apply: `tool_call_count += 1` twice and `enter_active` re-stamps the slot for one tool call. The count only feeds the hover tooltip (`tui/widgets/tooltip.rs`), so this is a per-tool-race cosmetic, not a lifecycle bug — a symmetric reverse-dedup would cost a second hot-path map write for a tooltip metric. Don't "fix" it by also counting in the JSONL arm; that IS the double-count. (Sibling of the #150 kind-asymmetry above.)

- **The `active_tasks` insert in `track_active_tasks` is not slot-gated, and that's HARMLESS — don't "fix" it with a `contains_key` guard.** Unlike the hook-wins dedup RECORD (which gates on `scene.agents.contains_key`), the insert runs even when desk exhaustion refused the id a slot, leaving a slot-less orphan `active_tasks[id]={tuid}`. That orphan EATS NOTHING (every reader — `suppress_subagent_leak`, the sweeps — is slot-guarded) and `tick`'s unconditional `active_tasks.retain(…contains_key…)` reaps it within one ~1s sweep. It does NOT preserve subagent-leak suppression across the exhaustion window (an earlier design pass wrongly claimed it was "the only carrier"): a desk only frees via `sweep_exited` at the 4.5s `EXIT_GRACE_WINDOW`, ~4 reaps later, so the orphan is long gone before a delegating parent could materialize — gated vs ungated is byte-identical (empirically checked). The asymmetry with the dedup record is cosmetic self-correcting debt, not load-bearing; leave it ungated to avoid churning the hot arm. (#612.)

- **The JSONL watcher's DECODED-event send is blockable, unlike the hook path's `CONN_TIMEOUT` — a deliberate asymmetry.** `walk_jsonl` awaits `tx.send(..)` on the bounded (`EVENT_CHANNEL_CAPACITY` = 256) reducer channel with no timeout. If the reducer stalls (a pathological hundreds-of-live-agents burst keeps the 256-deep channel full for seconds), the watcher's `select!` parks inside the notify arm's `walk_jsonl`, briefly pausing that source's OTHER arms (the 60s poll / instant-exit) until the reducer drains — a DELAYED-detection window, not a loss (the reducer's own `sweep_interval` still reaps stale slots, and it auto-recovers on drain). The hook ingress bounds the analogous exposure (`CONN_TIMEOUT` drops a parked `handle_conn` + logs `UndeliveredEvents`); the watcher's decoded-event send does NOT, because dropping a transcript delta would desync the per-file cursor's tail-follow (which assumes no gaps) — so don't add a naive send-timeout that drops JSONL events. The UPSTREAM `notify_rx` (holding `.jsonl` PATHS, not decoded events) IS bounded (`NOTIFY_PATH_CHANNEL_CAP`, #585) via `try_send`-drop-on-Full: a dropped PATH is safe (the cursor is untouched, so the poll / next notify re-walks it), which caps memory during the stall without risking a decoded-event gap.

- **CC now keys on the session UUID, not the transcript path.** The hook uses `IdKey::SessionId` (the `session_id` field); the watcher overrides `IdDeriver` with `cc_id_from_path` (the transcript filename stem, which equals that UUID); `decode_cc_line` re-derives the same UUID via `cc_id_from_path`; and `detect_parent_id` returns the `<parent-uuid>` directory component — the path segment immediately before `subagents/`. That component is the parent's own `cc_id_from_path` value, so the subagent→parent link is **cwd-split-safe**: even when the subagent transcript lands under a different project dir (a git-worktree cwd-split), only the cwd-derived prefix differs — the `<parent-uuid>` segment is identical. **Antigravity** (its keying) and CC's `SubagentStop` arm (the `agent_transcript_path` stem) fold a path through `id::normalize_path_key` (it lives in `id.rs` with the identity types, shared by the pixtuoid-scene palette's cwd key; identity on Unix; on Windows it strips a `\\?\`/`\\?\UNC\` verbatim prefix then folds `\`→`/` + casefolds — Antigravity emits backslash paths on Windows, NTFS is case-insensitive, and the `\\?\` strip (#197) is defensive so a `canonicalize`-style verbatim path still coalesces with its plain form). `AgentId::from_transcript_path` (the test/example shim) normalizes via that fn too, so test expectations stay platform-consistent by construction. Pinned by `tests/sources/decode/mod.rs::hook_and_watcher_keys_coalesce_for_one_file` (+ cfg(windows) twins). Don't add a CC keying site without routing it through `cc_id_from_path`; don't add an Antigravity site without `normalize_path_key`.

- **CC hook `transcript_path` always points to the PARENT'S transcript**, even when a subagent is the actor — so subagent TOOL hook events hash to the parent's `AgentId`. The reducer's `active_tasks: HashMap<AgentId, HashSet<String>>` suppresses hook `ActivityStart`/`End` for any agent currently inside a `Task` tool; JSONL has correct subagent attribution via the per-subagent transcript file at `<parent_uuid>/subagents/agent-<id>.jsonl`. The subagent→parent link is derived by `detect_parent_id` as the **`<parent-uuid>` directory component** — the path segment immediately before `subagents/` — which equals `cc_id_from_path` of the parent transcript; this is cwd-split-safe (a git-worktree subagent transcript lands under a different project-dir prefix, but the `<parent-uuid>` segment is identical). **Since #241 CC also decodes its OWN `SubagentStart`/`SubagentStop` hooks** (`claude_code::decode_cc_hook_custom`, dispatched via the registry's `hook.custom` exactly like Codex's — these change the event's SUBJECT to the child, inexpressible in the shared session-keyed arms): `SubagentStart` registers the child instantly with the parent link (the JSONL watcher's later `SessionStart` for the same transcript coalesces); `SubagentStop` emits the child's `SessionEnd` — the ONLY end signal a **Workflow-fleet** subagent gets (no per-agent `Agent` tool_use in the parent transcript → b1 structurally can't fire; no transcript end marker → finished fleet agents used to hold desks until the stale sweeps). **Keying nuance**: the wire `agent_id` is BARE hex (CC v2.1.170 capture) while the transcript filename stem — the watcher's id space — is `agent-<id>`; Start prefixes the wire id (tolerating an already-prefixed form without double-prefixing), Stop keys on `cc_id_from_path(agent_transcript_path)` (the authoritative key — exact watcher parity, covers the deeper `subagents/workflows/wf_*/` nesting) with the prefixed wire id as fallback. Captured wire fixture + cross-transport lifecycle regression: `tests/sources/claude/`. The Task signal travels as `ToolDetail::Task` (a typed enum variant on `AgentEvent::ActivityStart.detail`); the reducer pattern-matches on `d.is_task()` rather than scanning a free-form string. **`make_tool_detail` detects the subagent-dispatch tool SEMANTICALLY** — by the presence of `subagent_type` in the tool input — THE mechanism, with the single known name `Agent` (current CC) as the fallback for the rare input-less call. This is deliberate resilience: the dispatch tool was renamed `Task`→`Agent` (CC v2.1.63, **undocumented** — issue #29677), silently disabling suppression + b1 completion (the parent then shows the subagent's tools — observed live) until we keyed on the stable `subagent_type` field. Don't revert to name-only matching. **The legacy `Task` name arm was DROPPED in 0.12.0** (pre-v2.1.63 CC is too old to keep supporting): an old CC's real dispatch always carries `subagent_type`, so it stays caught semantically — only a name-only, input-less `Task` call lost coverage (accepted), and a `Task` dispatch WITH the field now fires the `unknown_dispatch` breadcrumb, correctly (an unrecognized dispatch name in the wild IS drift-worthy). A dispatch under any unrecognized name still works (semantic) and logs that `unknown_dispatch` drift breadcrumb (`source/drift.rs`, `warn!` on `pixtuoid::drift`) so the known-name set / docs can be updated. **Liveness flows UP the tree** (`scope::refresh_lineage`, in the Layer-B `state/scope.rs` module that owns the parent↔subagent tree ops): any `ActivityStart`/`ActivityEnd`/`Waiting` refreshes `last_event_at` for the actor AND every ancestor, so a delegating parent isn't stale-swept while a subagent is still working — whether the work arrives as a suppressed hook (misattributed to the parent) OR as the subagent's own JSONL (hooks are best-effort; this covers dropped ones). It's the mirror of `cascade_exit` (which pushes EXIT *down*). The suppress block relies on this up-refresh — don't drop it, or a single delegation > `STALE_ACTIVE_TIMEOUT` (10 min) would make the live parent look stale and the cascade would evict its still-working subagent.

- **JSONL watcher skips historical transcripts — on EVERY first-sight path, not just startup.** `walk_jsonl` in `source/jsonl/walk.rs` runs ONE first-sight gate (`should_seed_at_eof`) the first time *any* pass sees a file (the initial seed, the 250ms rescan, the 60s poll, a notify event): a `.jsonl` with mtime outside `DEFAULT_INITIAL_WINDOW` (currently 1 hour; configurable via `JsonlWatcher::with_initial_window`) **OR** carrying a `session_end`/`SessionEnd` marker (tail-scanned last `TAIL_BYTES`) has its cursor seeded at end-of-file and emits NO `SessionStart`; only a recent, not-ended file is read from the top. Symlinked ENTRIES under the root are refused wholesale before the gate (`walk_jsonl` stats via `symlink_metadata` — a planted dir symlink would recurse a loop / walk foreign trees into this source's id space; the root itself may still be a symlink, only entries are checked). Without this, ~hundreds of stale sessions saturate the desk allocator (capacity is auto-computed from terminal size; the headless fallback is `FALLBACK_DESKS=16` in `pixtuoid/runtime/mod.rs`). **"recent" is the source's own ACTIVITY clock where it has one, not the file mtime** — CC writes session-METADATA lines (`bridge-session`/`pr-link`/`last-prompt`/`relocated`/…) into transcripts belonging to OTHER, long-dead sessions, which bumps mtime and registered a days-dead session as a live sprite (capture-verified against CC 2.1.220, 2026-08-01). The `ActivityRecency` fn-ptr (`JsonlWatcher::with_activity_recency`, the `SourceDecoders` Strategy sibling of `SessionEndChecker`) answers "when did the SESSION last write?" from the same `TAIL_BYTES` tail the end-marker scan already reads (ONE const for both — a split would let a transcript be "ended" and "active" over different bytes). It returns a THREE-state `TailActivity`, and the third state is load-bearing rather than tidy: `At(secs)` gates on the newest turn, `Unknown` (nothing parseable / a turn line with no readable stamp) keeps mtime's verdict, and **`SidecarOnly` — a tail that parses but holds no turn at all — GATES**, because parseable-but-turn-less is EVIDENCE the recent write was metadata, not an absence of evidence. Measuring the reporting user's file is what forced that split: its `file-history-snapshot` line ran 7 KB, so the tail window opened mid-line and held that torn fragment plus seven sidecars with the newest turn entirely off-window — an `Option` collapsed that onto "no information" and fell straight back to the mtime the sidecars had just bumped. **Widening the window is not the fix** (these lines carry file contents, so no fixed window bounds them). **The gate alone closes only the COLD-START ordering** — once gated, a file is `known`, and revive-on-append is unconditional by design, so with pixtuoid already running (the normal case) the metadata append is what registers the ghost. Both registration paths therefore carry the same verdict: the normal append judges the APPENDED SPAN (`new_bytes` — exact, no window, no torn line), the oversized arm judges the tail. `revouch_gated_files` needs no guard — it reaches its cursor reset only past `probe_admits`, and the activity arm fires only when NOT vouched, so the two populations are disjoint. Accepted residual: an UNVOUCHED live CC session whose tail is momentarily all sidecar stays invisible until its next turn (the documented revive-on-append). "Unvouched" is wider than it reads — headless `claude -p`, a non-standard projects root, and **every CC session on Windows**, where `live_cc_session_ids` returns `None` by construction; a session with working hooks still registers through the hook plane, which is what keeps this bounded. An UNRECOGNIZED line type degrades to `Unknown`, never to sidecar evidence — reading a renamed turn type as "not a turn" would gate every live session at once, and this subsystem's drift doctrine is breadcrumb-and-self-heal. `TailActivity` lives in the always-compiled `decoder.rs` (the `LineDecoder` precedent — CC's decoder returns it and must build under `--no-default-features`), re-exported from `jsonl`. **Only CC supplies one** (`claude_code::cc_activity_recency`, over the `ACTIVITY_TYPES` subset of `KNOWN_TYPES` — membership is TURN-AUTHORSHIP, not whether we decode the type: `system` is the session speaking, `pr-link` is not); every other transcript source keeps pure mtime until the same write is OBSERVED on its wire — supplying one is a per-source wire fact, not a policy. The shared `decoder::rfc3339_to_epoch_secs` (hoisted out of grok's registry probe so the civil-date math has ONE copy) parses the stamps. mtime is only a liveness PROXY, so the gate composes with an optional ADDITIVE-ONLY **liveness probe** (`JsonlWatcher::with_liveness_probe`, refreshed once per scan pass; notify walks reuse the latest snapshot): a transcript whose `IdDeriver`-derived session id the probe vouches for bypasses the gate's RECENCY half — but NEVER its terminator half: a structural end marker is the SOURCE's own first-hand report that the session is over, which an mtime-independent liveness PROXY must not outrank (a vouch answers "is the owning process alive", never "is this session over" — omp's fd vouch fires for a bun tool merely READING an old transcript), so a vouched ENDED transcript is parked at EOF unregistered exactly like the oversized arm's `ended_in_skip` does, and `revouch_gated_files` re-runs the same check before resetting a cursor so the park cannot be undone once per scan pass. Accepted residual (the same one the oversized arm already takes): a session RESUMED onto a transcript whose last `TAIL_BYTES` still carry an old end marker stays invisible until its next append, which re-registers it through the normal revive. - **Agent removal needs a `SessionEnd`; abrupt exits have none and fall back to the slow stale-sweep.** A slot is GC'd `EXIT_GRACE_WINDOW` (4.5 s) after `exiting_at` is set, which only an `AgentEvent::SessionEnd` or `sweep_stale` sets. CC emits `SessionEnd` ONE way: the **hook** (best-effort — 200 ms write timeout, no retry, races CC's own teardown, so it drops silently); a dropped hook falls back to the idle sweep. There is NO durable JSONL fallback: modern CC persists no `/exit` record at all (slash commands are `type:"system",subtype:"local_command"` lines, and no transcript ends with an /exit user line — 135-transcript corpus), and the old content-based `<command-name>/exit</command-name>` matcher false-positived on messages QUOTING the wrapper, so it was removed — user-controllable content must never drive lifecycle (`cc_session_ended` now matches only structural `session_end`/`SessionEnd` markers, which CC doesn't write today; the upstream-drift watch flags it if that changes). **Ctrl-C / terminal-close / kill produce no signal either** (the process dies before the hook runs), and **Codex's `SessionEnd` hook is new and teardown-only (#710)** — upstream grew one (now an 11-variant `HookEventName`, verified vs `openai/codex` main, 2026-07-20) that fires only at graceful teardown (shutdown signals; reason const `other`), best-effort like CC's; `Stop` = turn end → Idle and `SubagentStop` = subagent end are still not session end. (It DOES fire `SessionStart`/`PreToolUse`/`PostToolUse` — see the multi-source-decoding note — but firing is version-unstable, so they're enrichment, not the lifecycle authority.) Those exits are reaped only by `sweep_stale` (Active 10 min / Idle 30 min / Waiting 60 min) — except where the liveness probe runs (macOS/Linux standard layouts): since #223 its NEGATIVE vouch (see the watcher edge above) ends a vouched-then-gone session in ~60–120s, leaving `sweep_stale` as the fallback for the probe's blind spots. For **CC** this is largely inherent — its clean exits usually signal via the hook, so the CC sessions that reach the long timeout are genuinely live-but-idle, abruptly killed, or the rare dropped-hook clean exit; a short CC silence-reaper would evict legitimately-idle live sessions (lunch-break idle), so don't add one. **Codex keeps its carve-out** because it still has no exit signal a short reaper could RELY on: the #710 `SessionEnd` hook covers only graceful teardown and is best-effort (an abrupt exit or a dropped hook writes nothing), no PID in any payload, and its internal `EventMsg::ShutdownComplete` is *not persisted* to the rollout (`should_persist_event_msg` → false; both verified against upstream `openai/codex`). So for abrupt/dropped-hook exits `sweep_stale` is still Codex's only reaper, and at the 30-min idle timeout an exited `cx·` sprite would ghost for half an hour. Codex Idle therefore uses the shorter `STALE_SHORT_IDLE_TIMEOUT` (5 min, in `state/reducer/mod.rs`, selected by the registry-derived `SourceCaps::short_idle_reap()` = `!has_exit_signal && resurrects_on_prompt` — Codex is the only row where both hold) — safe *specifically* for Codex because the only false-positive (a live-but-idle session past 5 min) is **self-healing**: its next `UserPromptSubmit` re-emits `SessionStart` and the sprite walks back in. **Since #220 the FD probe's `ProofOfLife` exempts a vouched Codex slot from this reap** — a slot whose rollout a live `codex` process still holds open is never short-idle-reaped; the reap effectively fires only once the probe stops vouching (process exited → fd closed → emissions stop), with the 5-min timer measured from the LATER of the last event and the vouch lapse (`PROOF_OF_LIFE_TTL` = 150s after the last emission). The self-healing property is unchanged — it now covers only the probe's blind spots (non-macOS/Linux platforms, a non-standard `--codex-sessions-root`). Pinned by `codex_vouched_idle_slot_outlives_short_idle_reap`. CC keeps the 30-min `STALE_IDLE_TIMEOUT` (its real `SessionEnd` hook makes a short reaper there all cost, no benefit). Pinned by `codex_idle_agent_reaps_faster_than_claude_idle` in `tests/reducer/liveness.rs`. **A stale-swept parent now cascades its whole subagent subtree** via the shared `scope::cascade_exit` (the parent↔subagent tree ops live in `state/scope.rs`; same `parent_id` BFS the `SessionEnd` arm uses) — so an abrupt-exit parent takes its subagents with it rather than orphaning them on their own longer stale timers. **Two guards stop the cascade from evicting a *live* subagent** (modeled on k8s liveness-vs-readiness): (1) **liveness up-propagation** — a working subagent keeps its ancestors fresh (`refresh_lineage`, see the `active_tasks` edge above); (2) **readiness exemption** — a subagent blocked under a `Waiting` ancestor (its permission `Notification` was attributed to the parent, so the parent is `Waiting` while the subagent stays `Active`) is skipped by `sweep_stale` via `has_waiting_ancestor` — "not ready", not dead. So the stale-sweep cascade only fires once the whole subtree is genuinely silent. **A subagent that COMPLETES is removed promptly too** (no 30-min linger), via a two-rung ladder: (1) **the `SubagentStop` hook (#241)** — CC fires it per finished subagent with `agent_transcript_path`, decoding to the child's own `SessionEnd` (instant, and the ONLY end signal for Workflow-fleet subagents, which have no per-agent `Agent` dispatch for b1 to drain); (2) **b1 Task-drain inference** for Agent-tool dispatches when that best-effort hook drops — CC writes no completion marker, so it's inferred: when the parent's last `Task` drains (`active_tasks[parent]` empties) the delegated subtree has returned, and `scope::cascade_exit(parent)` marks it exiting (the parent keeps running); the stale sweeps remain the backstop below both. **The b1 cascade is grace-DEFERRED, not immediate** (`B1_CASCADE_GRACE`, 2.5s, #151): a parallel second Task dispatch is suppressed as a leak and tracked only via its JSONL copy, so an immediate cascade at the first Task's drain would evict the second's LIVE subtree while that copy is still in watcher latency — unrecoverably (`exiting_at` has no clearer; after the GC the child's JSONL events no-op forever). Any Task insert inside the grace cancels the pending cascade (`pending_b1_cascades`); the drain's own tool_result write triggers the notify that replays the backlogged dispatch line, so one FSEvents hop is all the grace must cover. Don't "fix" the ~2.5s completed-subagent linger back to immediacy — and note the linger is unbounded for CHAINED dispatches: a sequential re-dispatch inside the grace defuses the pending entry, so the previous wave's completed children wait for the NEXT drain-to-empty (worst case the 30-min idle sweep) — the unavoidable price of never evicting a live subtree, since the cascade is whole-subtree. Residuals (consciously accepted, see #151): the chained linger above, and a sustained notify outage spanning the grace (both writes missed → 60s poll) can still evict early. A source with a clean completion signal would drive the same cascade through its own decoder; the scope ops stay source-agnostic.

- **A subagent registered AFTER its parent's cascade escapes it, and is reaped only by its OWN stale sweep — deliberate, because a parent's `exiting_at` is NOT a terminal verdict.** `cascade_exit` is a one-shot PUSH at the moment the parent exits; `register_slot` unconditionally inserts `exiting_at: None` and never consults the parent's. So a child SessionStart landing inside the parent's `EXIT_GRACE_WINDOW` (the CC path: the parent's `SessionEnd` hook fires at `/exit` while the subagent transcript's first-sight is still in FSEvents latency) — or any time after the parent is GC'd — registers alive under a corpse, ends up with a dangling `parent_id`, and holds a desk until its own idle timeout. Verified empirically, not reasoned. The two obvious fixes are both WRONG and were adjudicated against: REFUSING the registration breaks the live-parent-false-exit case (a negative vouch or stale sweep can wrongly end a LIVE CC parent, which then re-registers under the same session-UUID `AgentId` and silently re-adopts its children — refusing would permanently vanish a live subagent), and INHERITING the parent's `exiting_at` is the `B1_CASCADE_GRACE` hazard verbatim — `exiting_at` has no clearer, `sweep_stale`/`reconcile_connected` stamp it on sessions that may still be alive, and `resurrect_in_place` exists precisely because a root's exit is revocable, so inheritance would evict live subtrees unrecoverably. Note the grace window is the NARROWER half: once the parent slot is GC'd, `scene.agents.get(&parent)` is `None` and any parent-state-based guard falls through anyway. A durable fix must key on something that OUTLIVES the slot — the `child_ledger`, mirroring how #244-w2 already survives the 4.5s GC via `ended_at` — which is why this is tracked rather than patched at the register arm. Same accepted-residual class as the chained-dispatch linger below.

- **Resurrect-in-place starts from clean correlation state.** A `SessionStart` on an EXITING root slot cancels the walkout (`fsm::resurrect_in_place`) AND evicts the dead life's `active_tasks`/`gated_before_waiting`/`pending_b1_cascades` entries (mirroring `sweep_exited`, which never ran because the corpse never GC'd — a leftover tuid can never drain, so it would suppress every hook event of the new life); the `recent_proof_of_life` vouch deliberately survives (the resurrecting process is alive by definition).

- **Codex subagents (`spawn_agent`) are wired via the `SubagentStart`/`SubagentStop` HOOKS, not JSONL paths.** Unlike CC (whose subagent has a `<parent>/subagents/agent-*.jsonl` transcript → `detect_parent_id` derives the parent from the path; CC additionally decodes its own Subagent hooks since #241 — see the transcript_path edge above), a Codex subagent's rollout is FLAT (`~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl`), so the JSONL watcher renders it but ORPHANED. The hooks are the only carrier of the parent link: `SubagentStart`/`SubagentStop` payloads carry a distinct `agent_id` (the subagent, == its rollout-filename UUID) plus the parent `session_id`. `decode_hook_payload` keys the CHILD on `agent_id` (coalescing with that rollout) and emits `SessionStart{parent_id: session_id}` / `SessionEnd{agent_id}` — so the Codex subagent joins the SAME `scope` tree (cascade/liveness/readiness) as a CC one. Because the two transports race, `reducer::apply`'s `SessionStart` arm **enriches** an existing orphan's `parent_id` (rather than no-op-on-exists) when the JSONL slot was created first; it never re-parents an agent that already has a parent, and it **refuses any link that would close a `parent_id` cycle** (`scope::would_create_cycle`, checked at this ONE seam for both registration and enrichment — warn + degrade to parentless, #238): with cycles unable to exist, the scope walks need cycle guards only for termination, never correctness (a mutual-Waiting 2-cycle would otherwise exempt both members from `sweep_stale` forever). A MULTI-TURN Codex child (parent `send_input`) gets SubagentStop at EVERY turn end but no new SubagentStart — and NO other SessionStart carrier at turn N+1 from upstream (hook_runtime.rs verified 2026-06-11: UserPromptSubmit fires only for direct user input, non-Subagent events in a child's context carry the ROOT session_id). The carrier is manufactured by the **child-end un-claim side-channel (#246)** — the `SubagentStop`'s decoded `SessionEnd{as_child:true}` is observed by the CC hook tee and the Codex watcher then RELEASES the rollout's `seen` claim (drain-pending-bytes-first, no SessionEnd emitted, `seen`→`false` so the FD probe's re-vouch can't replay the still-open rollout) — so the turn-N+1 append first-sights a parentless SessionStart that the child-ledger re-link (see the hooks-proof-of-life edge above) re-parents; the same adoption covers the other parentless starts: a flat-rollout first-sight (#244-w1) and a post-exit revival. The two `CODEX_EVENTS` registrations (`install/codex.rs`) are therefore live, not dead — captured wire format is regression-pinned in `tests/sources/codex/mod.rs`.

- **Subagent display names come from `attributionAgent` in JSONL.** The decoder strips the plugin prefix (`feature-dev:code-explorer` → `code-explorer`) and emits `AgentEvent::Rename` so labels read meaningfully. Parents get their `cwd` basename instead. `cc_derive_label` falls back to the CC **project dir** (its name encodes the cwd path, `'/'→'-'`) when a Rename's seed line has no `cwd`, so an empty-cwd Rename never degrades `cc·dotfiles` back to a bare `cc`.

- **`AgentSlot.state_started_at` is `std::time::SystemTime`** — process-local in practice (no wall-clock anchoring). The pose system computes elapsed time relative to it for animation timing. **The whole `SceneState` tree derives `Serialize`/`Deserialize` (#279)**: the `Arc<str>`/`Arc<Path>` slot fields cross through owned `String`/`PathBuf` via the local `*_serde` adapters in `state/mod.rs` (serde has no blanket `Arc<T>` impl, and its `rc` feature wouldn't cover `Arc<Path>` — no `Box<Path>: Deserialize`). This exists for debug state dumps + the full-scene regression golden (`tests/reducer/snapshot.rs`, insta) — the serialized shape is NOT a stable wire contract, so adding a slot field is non-breaking (the golden just surfaces it for review). A v2 daemon snapshot/restore would build on this, but that consumer (and the multi-client #280 / remote-probe #281 prereqs) is deferred — closed as out-of-scope for the single-window, embedded-frontend direction.

- **`ActivityState::Active` ≠ "tool is currently executing".** CC fires PreToolUse → PostToolUse around every individual tool call, so without debouncing the slot flickers Active/Idle on every tool. The reducer treats `ActivityEnd` as "arm pending idle" (`AgentSlot.pending_idle_at`) instead of an immediate flip; the actual transition to `Idle` is realized by `reducer::tick` after `ACTIVE_GRACE_WINDOW = 1500 ms`. Any `ActivityStart` inside the window cancels the pending idle. Net: the slot reads as continuously Active for chained tool work, and visible Idle lags real Idle by up to 1.5 s + the 1 s sweep interval (≈ 2.5 s worst case). Don't add code that depends on `Active → Idle` being instant.

- **The reducer's permission `Waiting` resolves on the gated tool's PostToolUse.** A `PermissionRequest`/decision sets `Waiting`; the matching tool's `ActivityEnd` (PostToolUse) clears it (`gated_before_waiting` tracking). It is also cleared by `SessionEnd` + retained-eviction; `gated_before_waiting` is evicted at BOTH sites — `tick`'s `retain` and `sweep_exited`'s explicit `remove` (the apply-path eviction, pinned by `gated_before_waiting_evicted_on_apply_path_sweep`). A THIRD clear site lives on the Task-drain path (#152), CONDITIONAL on the drained tuid matching the gate: the drain deliberately skips the main arm (a Waiting parent keeps Waiting), so its gate entry would go stale and a late out-of-window JSONL replay of the same END would false-resolve a still-pending permission. The conditionality is load-bearing — an unconditional clear would wipe a parallel ordinary tool's gate (pinned by `task_drain_keeps_parallel_ordinary_tool_gate`). A FOURTH conditional site: the suppress-restore path only removes the gate when it holds a Task tuid (∈ `active_tasks`) — an ordinary tuid keeps Waiting + the gate (pinned by `suppressed_child_event_keeps_parents_own_parallel_tool_gate`). Keep the sites in sync if you touch eviction.
