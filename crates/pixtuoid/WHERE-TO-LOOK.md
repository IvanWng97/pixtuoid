# pixtuoid (binary) — where to look

Answers for the questions indexed in [`CLAUDE.md`](CLAUDE.md)'s
"Where to look". An entry earns its place only when landing on the
obvious symbol does NOT answer the question.

- "How do hooks get installed?" → `install::target::Target` is the multi-target registry; `install_target`/`uninstall_target` run the pure ConfigLock round (read→merge→backup→write, invariant #4); the in-TUI Sources panel (`s`) is the presenter (no `install-hooks` CLI — died in #284; `PIXTUOID_HOOK` is the one hook-path escape hatch). Per-target merge/format knowledge lives in that target's own `install/<cli>.rs`. Cross-target traps: Windows hook-command quoting is shared in `hook_cmd::windows` (#195); per-CLI home resolution mirrors each CLI's OWN resolver (`platform::home_first_dir`); `~`-expansion only for CLIs that expand it themselves (#342); detection probes the CLI's own dirs, never our artifact.
- "Where do runtime errors / config warnings surface?" (#157) → THREE sinks by failure class: the always-on warn-floor file log (`logging.rs::init` — the alternate screen owns the terminal); pre-altscreen stderr (config resolvers collect warnings that `main.rs` prints before `setup_terminal`; both feed the ONE emission point `config::warn_user`, which control-strips once); and the in-TUI source-health footer — a fatal `Source::run` exit publishes `SourceDeath` on a `watch` SIDE channel, deliberately not an `AgentEvent` (invariant #2).
- "How does config persistence work?" → `config.rs`; what grep won't tell you: an existing-but-unparseable config is NEVER rewritten; `resolve_theme` is the ONE validation site (CLI typo = hard error, config typo = warn+fallback); `[sources]` means explicit `true` only; `[[pets]]` keeps `kind` a raw String ON PURPOSE (a typed enum would make one typo wipe every setting) and stays the LAST field (array-of-tables serializes after scalars).
- "How do multi-floor offices work?" → engine half in `pixtuoid_scene::floor`; the binary boot-seeds capacity from real terminal size and grows it via `AtomicUsize::fetch_max`, monotone on purpose (shrink-direction shifts would remap floor-1+ agents onto wrong desks). The sweep is memoized by `tui::FloorCapacitySweep` (a `floor_capacity` call is a full layout compute). Shrunk-away agents stay alive and reappear when the terminal grows back.
