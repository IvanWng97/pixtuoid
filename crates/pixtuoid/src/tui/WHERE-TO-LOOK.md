# pixtuoid/tui — where to look

Answers for the questions indexed in [`CLAUDE.md`](CLAUDE.md)'s
"Where to look". An entry earns its place only when the question's own
words do NOT grep to the answer — it names a seam, a split, or a
chokepoint you would miss from the obvious symbol. Everything else is
the code's job to prove.

- "How is the office rendered (pixel pass → terminal)?" → world render = `pixtuoid_scene::pixel_painter::render_to_rgb_buffer`; the terminal flush = `tui::renderer::draw_scene` — the ONE consumer still on the raw call (it needs the full `PixelPassResult` mid-flush); every headless surface rides the shared `floor::render_floor` seam / `FloorSession` (#423).
- "How does the version popup render?" → `version_popup.rs` windows the wrapped notes through the shared `panel::window_range` but with its own `⋮ N more — see the link` marker, because this modal binds NO scroll key (pinned from both sides: `the_notes_marker_offers_no_scroll_and_fits_its_row` + `the_version_popup_binds_no_scroll_key`). The SHIPPED notes are a separate gate (the fixture-authoring tests stay green while the real arm truncates); both gates SKIP while `just bump`'s uncurated draft is in the tree. No committed PNG baseline on purpose — a threshold-0 diff would red on every intended notes edit.
- "How does the agent dashboard work?" → PURE model `tui::dashboard` + painter `widgets::dashboard`, whose one call site is the shared `paint_overlays` dispatcher (all three paint paths route through it — see the every-frame sharp edge). The `[xx]` badge comes from the shared `mod.rs::source_badge_span` (the ONE builder — dashboard, Sources panel, tooltip) and is deliberately not `REVERSED` on selection (a low-luminance hue inverted vanishes). Modal precedence: onboarding > help > version > connection > dashboard > theme-picker > normal.
- "How does the footer instrument work?" → the tier/policy MODEL is `pixtuoid_scene::footer::build_footer` (shared with the floating painter — the two surfaces can't drift); `widgets/footer.rs` is a thin adapter. The decode-drift half of `source_warning` comes from `ui_state.rs::DriftScan`, an incremental throttled log scan — the ONE deliberate exception to "no scan-the-history" (a passive diagnostic hint from a log artifact, never lifecycle state; a counting `tracing::Layer` was rejected for stateful blast radius on the global subscriber).
- "How does the Sources panel work?" → `s` toggles it — the SOLE way to bind/unbind (no install CLI). `build_rows` joins the registry to install targets via `install::target::by_source` (on `Target.core_source`, NOT `Target.name` — joining on name made the flagship row a no-op; `build_rows_makes_every_source_with_a_target_actionable`). Two facets, two lifecycles: CONNECTION is cached (rebuilt on open/toggle, never per frame), LIVE is per-frame and typed by source class — a Daemon counts INSTANCES through the shared `board::gateway_rollup`, the same rollup the footer chip reads, so the panel can't contradict it. Failures word through `connection::format_failure`, the ONE producer of the panel's failure sentences (onboarding's surfacing reuses it by construction).
- "How does first-run onboarding work?" → `setup::is_first_run` (config absent OR `[sources]` empty — but a DEGRADED config load is NOT a first run, or apply would fight the malformed-config-never-wiped rule). Apply routes through `sources::apply_choices`, SCOPED to the detected roster (never a declarative reconcile over every registered source); a Failed row opens the Sources panel ON that row with the panel's own wording. Skip (Esc) FREEZES each detected source's current state — `[sources]` becomes non-empty so onboarding never re-triggers, no hooks change, and the freeze reflects into the live gate (a pre-0.12 upgrader's hooked source goes live THIS session). Headless twin: `pixtuoid setup [--yes]`.
