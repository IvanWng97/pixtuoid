# pixtuoid tui painter — known sharp edges

Indexed one line each in [`CLAUDE.md`](CLAUDE.md). These look like bugs and are deliberate design — read the entry before "fixing" one. An entry states the edge, the WHY, and where the authority lives (the pinning test, the in-code comment, or the issue); the full adjudication history is in the cited issue/PR, not here.

- **`draw_scene` is called through `TuiRenderer`** (its inherent `render` flush), which owns the cross-frame state (per-floor `FloorCtx` as ONE `store` field on the per-frame `DrawCtx` borrow, plus the disjoint `buf`), delegates the world render to `pixtuoid_scene::pixel_painter::render_to_rgb_buffer`, then does the terminal-only half-block flush + widgets + footer. It returns a shared `Arc<Layout>` handle (memoized per frame — a refcount bump, not a deep copy), cached on `TuiRenderer.cached_layout` for the hit-tests; cleared during floor transitions.

- **The 6 borderless popups share ONE geometry authority — `panel::PanelGeometry`.** `compute(..) → outer()/inner()/cell_rect()` is PURE: the painter fills `inner()` and every click-target reads `cell_rect()` off the SAME compute, so paint and click cannot drift (the phantom-browser-launch class, killed structurally — the version popup's URL rect is a pure arithmetic test now). `PANEL_PAD_X/Y` is PRIVATE to `panel.rs`; the popups route through `panel::paint_panel` (auto-height + list windowing + the `⋮ N more ▾` cue), the version popup drives `PanelGeometry` directly. The shared backing's FLAT offset drop shadow (one factor, one offset, top-half-only bottom row) is a pinned USER PREFERENCE — don't "restore" a gradient/penumbra (`borderless_panel_casts_a_flat_offset_shadow`).

- **The board's ★ Star click target is `wall_board::star_hit_rect`, the same phantom-launch class** — it derives the `★ Star` span from the SAME board geometry the painter uses and clips to the scene. It replaced the loose `hit_test_branding` (which fired on all of cols 1..31). Keep paint and hit-rect deriving from the same `BOARD_W`/`BOARD_STAR`; the `debug_assert` in `paint_wall_display` pins the pairing.

- **The CLICK ladder (`tui/mod.rs`) and the HOVER ladder (`renderer.rs`) share the `agent > coffee > pet` ordering AND the underlying hit-tests, but a unified `resolve_pointer_hit` resolver is NOT worth hoisting.** The primitives ARE shared already; what blocks a resolver: the two live in different layers with different data, the target sets differ (click has star/focus, hover has mascot/furniture), and the click FUSES test+act in `focus_clicked_agent`. A resolver would be a param-heavy shim as wide as the body it hides. Adjudicated in sweep-3 (an earlier draft wrongly claimed the agent primitive diverges — it does not); the ordering stays synced by the load-bearing comment in the click arm.

- **Every modal overlay paints on EVERY frame — including the footer-only ones.** On a classic 80×24 the office can't lay out — 24 rows are under `layout::min_layout_size` — and rendering falls to `draw_footer_only_frame`, but every key handler stays live — so overlay state travels as ONE `renderer::OverlayFrame` through all THREE paint paths, and panels self-guard on size via `PanelGeometry` (first run opens onboarding INTO the footer-only path; the too-small notice paints after the overlays, not before). The footer row is protected inside the geometry (`panel::RESERVED_FOOTER_ROWS` clamps in `compute` — reserving there rather than shrinking callers' bounds keeps every already-fitting panel from moving a row and silently redrawing committed images), and the drop shadow separately clips itself to `renderer::scene_rect` (the shadow band dims fg only, which a string assertion can't see — a bigger symmetric reserve was priced and rejected). `renderer::FOOTER_ROWS` is the one row-count all three readers share.

- **Every crossterm key event passes `should_dispatch_key` first**: Windows delivers Press AND Release (and Repeat) per keystroke, so only `KeyEventKind::Press` dispatches — otherwise toggle keys double-fire there. Unix only emits Press, so the gate is a no-op locally.

- **The `w` walkable/approach/route debug overlay is dev-only** — its dispatch arm is `#[cfg(debug_assertions)]`-gated, so release builds silently ignore `w`. Don't "fix" a report that `w` does nothing in an installed binary.

- **`run_tui` is the `block_on` ROOT future, not a tokio worker — `block_in_place` there is INERT.** `driver.rs` does inline `rt.block_on(run_async)`; the loop body runs on the `block_on` thread, which owns no worker core, so `block_in_place` runs the closure inline with zero scheduling effect (removed as proven inert in #603 — it does NOT panic; that's `current_thread`-only). The loop's one-shot blocking I/O (Sources panel, onboarding apply, config save, `focus_slot`) is an ACCEPTED ms-scale inline stall — the `flock` is `try_lock`, and `reducer_task`/sources run on their own worker threads. `spawn_blocking` was rejected: non-`Send` borrows would force a pending-op state machine in the codecov-ignored loop AND widen `focus_slot`'s #527 pid-recycle guard window.
